# What a good test is

A test verifies **behavior through a public interface**, not implementation details. The code behind it can change entirely; the test shouldn't. A good test reads like a specification: `test_non_numeric_order_id_is_missing` says what capability exists, and it survives refactors because it doesn't care how the code is organized.

## Properties

- **Named after the behavior**, not the AC number or the function: `test_rejects_query_on_raw_schema`, not `test_ac6` or `test_referenced_tables`. The ticket keeps the AC → test mapping.
- **Arrange / Act / Assert**, each part visible. One behavior per test; several asserts are fine when they check the same outcome (the AC's *Then* and *And*).
- **Expected values from an independent source of truth**: a literal from the AC, a worked example, a figure computed by hand. Never recomputed the way the code computes it.
- **Deterministic and fast**: no real LLM, network, clock or randomness (see `mocking.md`). The whole folder suite should run in seconds, so it gets run after every green.
- **Independent**: runs alone and in any order. Reset shared state in fixtures (`clear_sessions()` in triage), and only share read-only resources (the session-scoped DuckDB `con` in `travel-agency`).
- **Typed like production code**: test functions annotated (`-> None`), fixtures with their types, `pytest.mark.parametrize` for the boundaries of one rule.

```python
@pytest.mark.parametrize(
    ("order_id", "is_valid"),
    [("123", False), ("1234", True), ("1234567890", True), ("12345678901", False)],
)
def test_order_id_length_boundaries(order_id: str, is_valid: bool) -> None:
    state = ConversationState(process_type=ProcessType.delivery_delay, order_id=order_id)

    state = apply_business_rules(state)

    assert ("order_id" not in state.missing_fields) is is_valid
```

## Red for the right reason

| Failure | Is it a valid red? |
|---|---|
| `AssertionError: assert [] == ['order_id']`: the value the AC describes is wrong | Yes |
| `assert 200 == 422`: the API doesn't reject yet | Yes |
| `ModuleNotFoundError: No module named 'text2sql.guard'`: the module this cycle creates | Yes, in the cycle that creates it |
| `fixture 'con' not found`, `NameError` from a typo, importing the wrong path | No: the test is broken |
| `duckdb.PermissionException` when the AC expects a controlled rejection message | No, if the assertion is on the message: the test passes or fails for a reason outside the behavior. Assert on what the AC says. |
| A test that passes at once | No (see the table in `SKILL.md`), unless it is an agreed guard |

## Anti-patterns

### Implementation-coupled

It mocks internal collaborators, tests private functions, or verifies through a side channel instead of the interface. The tell: it breaks when you refactor, though the behavior hasn't changed.

```python
# ❌ Reads the session store directly and patches an internal helper
def test_order_id_stored(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setattr("app.domain.business_rules._normalize_order_id", lambda v: v)
    client.post("/cases/T-1/events", json={"message": "Order 8921"})
    assert store._SESSIONS["T-1"].state.order_id == "8921"


# ✅ Through the public API, as a caller sees it
def test_order_id_stored() -> None:
    client.post("/cases/T-1/events", json={"message": "I want to return an item."})
    client.post("/cases/T-1/events", json={"message": "The order number is 8921."})

    state = client.get("/cases/T-1/state").json()["state"]

    assert state["order_id"] == "8921"
```

### Tautological

The assertion recomputes the expected value the way the code does, so it passes by construction and can never disagree with the code.

```python
PRICES = {"cost": {"input_cost_per_1m_tokens": 3.0, "output_cost_per_1m_tokens": 15.0}}


# ❌ Same formula as the code (triage `app/utils/observability.py`): if it is wrong, both are wrong
def test_estimate_cost() -> None:
    expected = 1_000 * 3.0 / 1_000_000 + 500 * 15.0 / 1_000_000
    assert estimate_cost(1_000, 500, PRICES) == expected


# ✅ A figure worked out by hand: 0.003 $ of input + 0.0075 $ of output
def test_estimate_cost() -> None:
    assert estimate_cost(1_000, 500, PRICES) == pytest.approx(0.0105)
```

The same applies to a snapshot generated by running the code, or a constant asserted equal to itself.

### Horizontal slicing

All the tests first, then all the implementation. Bulk tests verify *imagined* behavior: they test the shape of things, become insensitive to real changes, and fix the test structure before you understand the implementation. Work in vertical slices: one test → one implementation → repeat, each test a **tracer bullet** that responds to what the last cycle taught you.

### Asserting model quality in a unit test

`assert "refund" in response.assistant_message` against a real or mocked LLM tests the model, or the mock you wrote, not the code. Whether the model answers well is **evaluation** (`eval/` in triage, phase 10 in travel-agency) with its own cases and repetitions. Unit tests check the deterministic code around the model: what happens when it returns invalid JSON, which operation the rules choose from a given state, whether the guard rejects a bad SQL.

### Weakening to get green

Loosening `==` to `in`, catching a broad `Exception` in the test, `@pytest.mark.skip`, or editing an earlier test's expected value. All of these hide a behavior change. Stop and agree it with the user instead.

### Asserting the whole response when one field matters

`assert response.json() == {...30 fields...}` breaks on every unrelated change and hides what the AC cares about. Assert the fields the AC names.
