El Asistente DropLab: cómo se conecta todo

En las sesiones 1 y 2 vimos las piezas una a una: llamar a un modelo, una herramienta que es una función de Python, la capa semántica, Whisper, el RAG. En la sesión 3 las unimos en un asistente que se usa desde el navegador, y el código creció. Esta guía lo recorre en orden, archivo a archivo, con las líneas importantes de cada uno. No hace falta entender cada línea: hace falta saber qué pieza hace qué.

Todo en practica/sesion_3/Rutas desde la carpeta DropLab_sesion_3unos 30 minutos de lectura

La idea en una frase

No hay nada nuevo por dentro: son las funciones de Python de las sesiones 1 y 2. Lo nuevo son tres piezas que las conectan: LangGraph las ejecuta en orden, FastAPI las pone detrás de una dirección web y Open WebUI es la ventana.

Y el reparto de siempre

El modelo hace dos cosas: propone un plan (rellenando un JSON con opciones cerradas) y redacta la respuesta. Todo lo demás —calcular, buscar, comparar, comprobar, decidir el orden— lo hace nuestro código.

Desde la terminal, 05_flujo.py empieza directamente en el paso 4: llama al flujo sin API ni Open WebUI. Por eso se puede probar todo en la terminal. La guía va de dentro hacia fuera: primero las piezas (pasos 1–3), luego el flujo que las organiza (4–6) y por último cómo se abre al exterior (7–8).

Ábrelo en tu editor: practica/sesion_3/asistente/flujo.py, línea 45. En verde, las líneas importantes.
  • Plan: lo único que el modelo puede proponer. Literal es una lista cerrada: imagen, cifras o documentos. Cualquier otra cosa no pasa la validación.
  • Estado: la «carpeta» que pasa de un paso al siguiente: la pregunta, la imagen, las consultas, los fragmentos, la respuesta… Cada paso lee lo que necesita y añade lo suyo.
  • Annotated[…, operator.add]: la traza y los errores se van sumando (cada paso añade su línea), en lugar de sustituirse.

Diferencia con la sesión 1: allí le dábamos al modelo un menú de herramientas (tools) y él decidía cuándo llamarlas. Aquí el modelo solo marca casillas en el plan, y es el código quien llama a cada función, en orden. Menos libertad para el modelo, más control para nosotros.

Para vuestro proyecto: si el modelo tiene que elegir algo, dadle opciones cerradas con un esquema y validadlas. Nunca texto libre que luego haya que interpretar.

Al ejecutar, LangGraph avisa cada vez que termina un paso: así salen las líneas ▸ de la terminal y el progreso en Open WebUI. Y el mismo proceso sin LangGraph, con un while, está en asistente/flujo_simple.py (unas 25 líneas): da el mismo resultado.

Para vuestro proyecto: un framework de flujos no hace el trabajo: lo organiza. Para pocos pasos, un bucle de Python vale. Compensa cuando hay ramas, reintentos, pausas para que una persona apruebe o hay que reanudar a medias.

Vuestra propia integración, paso a paso

La receta que hemos seguido, para aplicarla a otro problema:

  1. Funciones que hacen una cosa y se prueban solas: una consulta, una búsqueda, una lectura. Sin modelo.
  2. Una función para hablar con el modelo, con tiempos y errores con nombre (como ollama.py).
  3. Esquemas con Pydantic para todo lo que entra y sale de un modelo: lo que propone y lo que extrae.
  4. El proceso: primero con funciones y un bucle de Python; LangGraph cuando crezca (ramas, reintentos, aprobación humana).
  5. Comprobaciones en código después del modelo: que lo que dice esté en las fuentes; lo que no se puede comprobar, se dice.
  6. Una API con FastAPI que solo valida y llama a vuestras funciones. /docs sale gratis.
  7. Una interfaz como adaptador fino de la API (Open WebUI, una web, un bot de chat…).
  8. Medir por piezas: un examen para la recuperación, otro para las cifras, otro para las respuestas (06_evaluar.py). Así sabéis dónde falla, no solo si falla.

Para profundizar: hacia producción

Lo que hemos montado funciona y está medido, pero es un prototipo de aula. Esto es lo que haría falta para que una empresa lo usara cada día. Son ideas para quien quiera seguir; no hace falta hacerlas todas.

La idea

Las piezas ya están. Llevarlo a producción es sobre todo medir (saber si funciona y cuándo deja de hacerlo), proteger (quién puede ver qué) y operar (que funcione cada día y se note cuando falla).
